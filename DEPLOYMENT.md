# Deployment

Backend on **Render** (Docker + persistent disk), frontend on **Vercel** (static SPA).

The two deploys reference each other, so they have to be wired up in a specific
order — the backend needs the frontend's URL for CORS, and the frontend needs the
backend's URL baked into its build. Follow the steps in order; step 4 closes the loop.

---

## Before you start: the SQLite constraint

The backend keeps its data in a single SQLite file. For that file to survive a
redeploy or restart it must live on a **persistent disk**, and Render only offers
disks on **paid instance types**.

On Render's free plan:

- the filesystem is ephemeral, so every redeploy or restart **resets the registry to empty**, and
- the service spins down after inactivity, so the first request after idle is slow.

`render.yaml` therefore specifies `plan: starter`. Confirm the current price on
Render's pricing page before deploying — it was around $7/month at the time of
writing, but check rather than trust this number.

If you would rather not pay, your options are:

- **Deploy on free anyway** and accept that the database resets. Fine for a demo
  you reseed by hand; not fine if anyone is meant to keep an account.
- **Move to PostgreSQL** instead, which Render offers a managed instance of. See
  [Moving to PostgreSQL](#moving-to-postgresql) below.

---

## Configuration reference

Everything environment-specific is read from configuration. Nothing below needs a
code change to set. ASP.NET Core maps `__` in an environment variable name to `:`
in configuration, so `Jwt__Key` sets `Jwt:Key`.

| Variable | Where | Purpose |
| --- | --- | --- |
| `ASPNETCORE_ENVIRONMENT` | Render | `Production`. Also disables Swagger. |
| `ASPNETCORE_URLS` | Render | `http://+:10000` — the port the container listens on. |
| `Database__Path` | Render | `/var/data/app.db` — must be inside the mounted disk. |
| `Jwt__Key` | Render | Token signing secret. Must be 32+ bytes. |
| `Cors__AllowedOrigins__0` | Render | The exact Vercel origin, no trailing slash. |
| `VITE_API_URL` | Vercel | The Render backend URL, no trailing slash. |

Two guards exist so a misconfigured deploy fails loudly at startup instead of
misbehaving later: the app refuses to boot outside Development if `Jwt:Key` is
still the placeholder committed in `appsettings.json`, or if the key is shorter
than 32 bytes.

## 1. Deploy the backend to Render

1. Push this branch to GitHub (`render.yaml` must be on the branch you deploy).
2. In Render: **New → Blueprint**, select this repository, and let it read
   `render.yaml`. It creates one web service plus a 1 GB disk mounted at `/var/data`.
3. Render will prompt for the env vars marked `sync: false`. Leave
   `Cors__AllowedOrigins__0` blank or put a placeholder — you do not know the
   Vercel URL yet and will set it in step 4.
4. `Jwt__Key` is generated by Render automatically. Do not paste one in, and do
   not commit it anywhere.
5. Deploy, then confirm the service is healthy:

   ```bash
   curl https://<your-service>.onrender.com/health
   # {"status":"ok"}
   ```

Migrations run automatically on startup, so the schema is created on first boot.
Swagger is **not** served in Production.

Copy the service URL — you need it next.

---

## 2. Deploy the frontend to Vercel

1. In Vercel: **Add New → Project**, import this repository.
2. Set **Root Directory** to `client`. This is required: the repo root has no
   `package.json`, so the build fails without it. `client/vercel.json` supplies
   the build command, output directory and the SPA rewrite.
3. Add an environment variable:

   | Name | Value |
   | --- | --- |
   | `VITE_API_URL` | `https://<your-service>.onrender.com` |

   No trailing slash. Add it for Production (and Preview, if you want preview
   deploys to work).
4. Deploy, and copy the resulting `https://<project>.vercel.app` URL.

> **`VITE_API_URL` is baked in at build time**, not read at runtime. Changing it
> later requires a **redeploy**, not just an env var edit.

---

## 3. Verify the SPA rewrite

The app uses `BrowserRouter`, so routes like `/dashboard` and `/skills/12` exist
only on the client. Without the rewrite in `client/vercel.json` those URLs 404 on
a hard refresh. Check by loading `https://<project>.vercel.app/login` directly —
it should render the login page, not a 404.

---

## 4. Close the loop: point CORS at the frontend

Back in Render, set the env var to the exact Vercel origin:

```
Cors__AllowedOrigins__0 = https://<project>.vercel.app
```

No trailing slash, and the scheme must match. Save — Render redeploys. Until
this matches the browser's origin exactly, every API call from the deployed
frontend fails with a CORS error while the backend itself looks perfectly healthy.

To allow more origins (a custom domain, say), add `Cors__AllowedOrigins__1`,
`Cors__AllowedOrigins__2` and so on.

---

## 5. Smoke test

1. Open the Vercel URL and register an account.
2. Log in, upload a skill, add a tag, save a second version, view the diff.
3. Hard-refresh on a deep link such as `/dashboard`.
4. Redeploy the Render service, then confirm your account **still exists** — this
   is what proves the persistent disk is actually working. If you are logged out
   and your data is gone, the disk is not mounted and you are on ephemeral storage.

## Moving to PostgreSQL

`server/Program.cs` reads `Database:Provider`, and the `postgres` branch
intentionally throws with instructions rather than silently failing. Switching
over takes three steps:

1. Add the provider package:

   ```bash
   cd server
   dotnet add package Npgsql.EntityFrameworkCore.PostgreSQL --version 8.*
   ```

2. Replace the `case "postgres":` branch in `Program.cs` with:

   ```csharp
   case "postgres":
       options.UseNpgsql(builder.Configuration.GetConnectionString("Default"));
       break;
   ```

3. **Generate a Postgres migration set.** EF Core migrations are
   provider-specific — the existing ones in `server/Migrations/` emit SQLite SQL
   and cannot be reused. This is the real work in the switch, and the reason it
   is not a pure config change:

   ```bash
   dotnet ef migrations add InitPostgres --output-dir Migrations/Postgres
   ```

   Existing SQLite data is **not** carried over; you would need to export and
   reimport it separately.

Then set `Database__Provider=postgres` and `ConnectionStrings__Default` on Render,
and drop the disk from `render.yaml`.

## Troubleshooting

### Every API call fails with a CORS error, but `/health` works

`Cors__AllowedOrigins__0` does not exactly match the browser's origin. Compare
scheme, subdomain and trailing slash. A Vercel **preview** deploy has a different
hostname than production, so it needs its own entry.

### Backend boots, then immediately crashes

Check the Render logs for one of the startup guards:

- `Jwt:Key is still the development placeholder` — `Jwt__Key` is not set on the service.
- `Jwt:Key must be at least 32 bytes` — the secret is too short for HMAC-SHA256.
- `Unknown Database:Provider` — typo in `Database__Provider`.

### Data disappears after every deploy

The disk is not mounted, or `Database__Path` points outside it. It must be inside
`mountPath` (`/var/data/app.db` for the default blueprint). Free-plan services
cannot have disks at all.

### `VITE_API_URL is not set` in the deployed frontend

The env var was not set in Vercel, or was added after the last build. Set it and
**redeploy** — it is read at build time.

### Frontend deep links 404

The SPA rewrite is missing. Confirm Root Directory is `client` so
`client/vercel.json` is actually picked up.

### First request after idle takes ~50 seconds

A free-plan Render service spun down. Expected on free; paid instances stay warm.
